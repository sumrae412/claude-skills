# Opportunity Solution Tree

Structured product discovery framework from Teresa Torres' *Continuous Discovery Habits*. Maps a desired outcome through opportunities (customer needs) to solutions and experiments.

Use when: deciding what to build next, prioritizing features, exploring a problem space before solutioning, or designing experiments to validate assumptions.

## Framework Structure

Four levels, top to bottom:

```
🎯 Desired Outcome
    ┣━ 💡 Opportunity 1
    ┃    ┣━ 🛠 Solution 1a
    ┃    ┃    ┗━ 🔬 Experiment 1a-1
    ┃    ┃    ┗━ 🔬 Experiment 1a-2
    ┃    ┗━ 🛠 Solution 1b
    ┃         ┗━ 🔬 Experiment 1b-1
    ┗━ 💡 Opportunity 2
         ┗━ 🛠 Solution 2a
              ┗━ 🔬 Experiment 2a-1
```

## The Four Levels

### 1. Desired Outcome

A single, measurable business metric. One outcome per tree. Examples:
- "Increase landlord activation rate from 30% → 60% in first 14 days"
- "Reduce tenant dispute response time from 48h to 4h"
- "Improve trial-to-paid conversion by 20%"

### 2. Opportunities

Customer needs, pain points, or desires framed from their perspective. Phrased as "I struggle to..." or "I wish I could..."

Focus on opportunities before solutions. Prioritize opportunities using:

```
Score = Importance × (1 − Satisfaction)
```

Where Importance and Satisfaction are rated 1-5 each.

### 3. Solutions

Multiple potential ways to address each opportunity. Minimum 3 solutions per opportunity to avoid the "first idea" trap. Generated by the Product Trio (product, design, engineering).

### 4. Experiments

Fast, cheap tests to validate assumptions about each solution. Test across four dimensions:
- **Value** — will users engage with it?
- **Usability** — can users figure it out?
- **Viability** — does it work for the business?
- **Feasibility** — can we build it?

## Workflow

1. **Define the outcome.** One metric, one tree.
2. **Map opportunities.** Interview customers, analyze support tickets, review analytics. Phrase from the customer's perspective.
3. **Brainstorm solutions.** At least 3 per opportunity. No filtering during ideation.
4. **Design experiments.** Smallest test that would validate or invalidate each solution. Prefer cheap/fast (interviews, prototypes) over expensive/slow (full builds).
5. **Update weekly.** Discovery is continuous. Update the tree every week based on new learnings. Solutions that fail experiments are pruned; surviving solutions move toward build.

## Scoring rubric

| Level | Pass criteria | Fail signal |
|---|---|---|
| Outcome | Measurable, attributable to product work, time-bound | Subjective, vague, or not a metric |
| Opportunity | Rooted in customer evidence, not assumption | "I think users want X" with no evidence |
| Solution | 3+ per opportunity, diverse approaches | One idea per opportunity, or all similar |
| Experiment | Tests a specific assumption, cheap enough to run this week | Requires a full build to validate |
